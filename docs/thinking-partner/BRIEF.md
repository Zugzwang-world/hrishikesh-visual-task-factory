# BRIEF: Visual Task Factory (3D robot workcell)

Agreed 23 Nov 2026. Canonical copy: docs/thinking-partner/BRIEF.md in the public repo hrishikesh-visual-task-factory.

## The bet in brief

We build a 3D visual task factory for robot perception. It generates photoreal tabletop scenes in Blender, asks the questions a robot must get right, and proves every answer from the scene file with checks that never ask an AI model. Most teams will submit 2D charts or documents. We go one dimension further, into the physical world Innodata calls its next big market.

- **The family:** one image family, a robot workcell. That means a table of everyday objects seen through the robot's cameras: overhead, front and gripper-mounted.
- **Why 3D:** robots now rely on vision-language models to see, so a spatial mistake becomes a wrong grasp or a collision. A 3D scene gives exact truth for depth, distance, occlusion and counts. No 2D generator or AI image model can.
- **The niche:** 3D alone isn't new (CLEVR did it in 2017). Our niche is a factory for the questions a robot needs answered exactly: what's nearest the gripper, what's reachable, how hidden something is, what's stacked on what, how many in clutter.
- **Not a simulation:** a physical-twin set. We arrange real objects exactly as generated scenes say and photograph them, so real photos carry exact answers.
- **Ready to adopt:** a renderer-independent scene spec, YAML recipes, bring-your-own objects and models, Docker, offline generation, and exports for robot learning (training data and verifiable rewards).
- **Demo:** a Task Explorer web viewer. Rotate the 3D scene, switch robot cameras, and see each question, its true answer and every model's answer.
- **Why it wins:** it meets every stated requirement (Part 4) and puts most effort where half the score sits: repeatability and validation evidence.
- **How we work:** prototype quality, built directly, with no licence, compliance or production work and no formal test gates beyond the checks the judges score. If 3D genuinely blocks us, the same engine can switch to financial price charts.

## Part 1: The problem in plain words

Build a system that keeps producing new sets of image, question and correct answer. It must prove each answer without trusting an AI, then use the sets to test frontier vision models and report where they fail.

Think of a machine that prints unlimited new exam papers, each with a guaranteed answer key, and then grades the best AI students on them. Because our code draws each image from data we chose, we already know the true answer. Fresh images also can't be in any model's training data, so the test is fair.

One task, using the organizers' own card example (bar chart, "Which bar is tallest, and by how much?", answer "B, by 28"):

| Piece | What it is |
| --- | --- |
| Image | Generated by the pipeline |
| Question | Answerable only by looking at the image |
| Reference answer | Computed from what the generator drew |
| Checking method | A reliable way to mark a model's answer right or wrong |
| Validation evidence | Proof the task is answerable and the answer is correct |

The official statement asks for five things:

1. **A real problem that matters.** Name the real-world job that needs the visual skill, and say what goes wrong when an AI gets it wrong.
2. **A system, not a one-off dataset.** It must be automated and repeatable. Clint said "the keyword is repeatable" and asked teams not to hard-code; any manual edit must be disclosed with a reason.
3. **Questions that need the image.** No answer from text alone, and the image holds all the evidence needed.
4. **Answers set independently of the model under test.** A model may never write the answer key it is then graded on.
5. **A real model evaluation.** Run frontier models on the tasks and report their strengths and weaknesses. Clint barely mentioned this, but the official text spells it out, and many teams will skip it.

What to submit: a public GitHub repo, documentation, a working prototype, a demo video, and slides on the organizers' mandatory template ([template](https://docs.google.com/presentation/d/1fXZJ86GvJ-UnR4C7CkeWoTnzNqC7-gznV7efty8Su50/edit)). Finalists do a live demo on 20 Dec.

Read "the answer must be in the image" as "all evidence must be visible". Their own example answer, "by 28", is a subtraction, so computed answers are fine.

## Part 2: How you're scored

Half the score (25% + 25%) rewards proof: a pipeline judges can rerun, and evidence that each task is valid. Most teams will spend their time on prettier images. We spend ours on proof.

| --- | --- | --- | --- | --- |
| Working, repeatable implementation | 25% | "The keyword is repeatable"; no hard-coding; disclose manual changes | A pipeline a judge can rerun and get the same tasks | One command rebuilds any task from its seed; scene files and answers byte-identical everywhere; CI proves it |
| Validity and validation evidence | 25% | Show the task is solvable and the checking works | Evidence, not claims | Eight-gate report per task and per dataset, founder audit, physical-twin photos, log of rejected tasks |

Two traps: colour and text swaps don't count as variation, and a generator with no evaluation leaves the "evaluate frontier models" half of the official brief unanswered.

### Why 3D, and why a robot workcell

- Robots increasingly use vision-language models to see and plan, and those models struggle with spatial reasoning ([RoboSpatial](https://arxiv.org/abs/2411.16537)).
- A wrong spatial answer becomes a physical error: the wrong object grasped, a collision, a missed item.
- 2D generators can't give exact depth, distance or occlusion. AI image generators can't even guarantee counts: a 2025 benchmark found every state-of-the-art diffusion model it tested generated wrong object counts ([T2ICountBench](https://arxiv.org/abs/2503.06884)). A 3D engine knows where every object is, so the truth is exact.
- Clint pointed us to CLEVR, which is itself a 3D-rendered scene dataset. We are its direct descendant, aimed at robots.

### Where we stand against existing work

| Work | What it is | Our difference |
| --- | --- | --- |
| [CLEVR](https://arxiv.org/abs/1612.06890) | 3D-rendered toy shapes with program-generated questions (2017) | Real-world objects, robot cameras, robot-relevant questions |
| [RoboSpatial](https://arxiv.org/abs/2411.16537) | Real 3D scans and egocentric images of indoor and tabletop scenes, for training | Unlimited new scenes with exact answers and controllable difficulty |
| [OmniSpatial](https://arxiv.org/abs/2506.03135) | Spatial-reasoning benchmark; notes the latest reasoning models score 90%+ on existing basic benchmarks | We skip saturated left/right questions and target what robots need exactly |
| [Spatial-DISE](https://arxiv.org/abs/2510.13394) | Spatial VQA built with a Blender pipeline, about 12K pairs | A reusable factory with gates, twins, physical twins and an eval harness, not a fixed set |
| [Embodied3DBench](https://arxiv.org/abs/2605.29074) | Robot-centric benchmark; models relatively strong on high-level object-to-object relations | Exact low-level quantities, clutter and counterfactual twins |

### Seven moves that set us apart

1. **Answers computed from the 3D scene** by typed programs, the method CLEVR used.
2. **Two independent computations.** One from the scene file, one from the rendered mask and depth passes. They must agree.
3. **Counterfactual twins.** Move one object and re-render: the answer must change. This builds on [VQA v2's complementary pairs](https://arxiv.org/abs/1612.00837).
4. **Multi-view consistency.** The same scene from three cameras: does the model agree with itself?
5. **Physical twins.** Real objects arranged exactly as generated layouts say, then photographed, giving exact answers on real photos.
6. **Breaking-point curves and automatic error attribution:** wrong depth, wrong object, miscount, invented object.
7. **Dual use.** Training data and verifiable rewards for robot learning, both of which Innodata sells.

One principle runs through all of it: no AI image generator anywhere in the image path.

## The family in depth: robot workcell scenes

One image family: a table of everyday objects seen through a robot's cameras. Every scene is built from a seed, rendered in Blender, and stored as a scene file that holds the exact truth.

**Scene spec (the world state).** A renderer-independent JSON file listing the table, every object (asset ID, pose, scale, material), stacks and containers, the gripper pose, marked zones, cameras (pose and lens), lighting and the seed. Answers are computed from this file alone.

**Objects.** About 40 everyday objects (mugs, bowls, bottles, boxes, fruit, tools) from Poly Haven, plus procedural boxes and cylinders of exact size as scale references. Poly Haven releases all its assets as CC0, usable for any purpose including training AI models ([Poly Haven FAQ](https://docs.polyhaven.com/en/faq)).

**Layout.** A sampler places objects under constraints (clutter level, stacks, objects inside containers). A short rigid-body drop then lets them settle into natural resting poses, and the settled poses are written back into the scene file, so the truth always matches what was rendered.

**Cameras.** Overhead, front and gripper-mounted, each with a jittered pose. A camera-quality dial adds lens distortion, sensor noise, motion blur, low light and a CCTV look.

**Rendering.** Blender runs headless, without a window, using Cycles with a fixed sample seed. We render on the Mac first, then on the DGX Spark if a source build of Blender works there, with a cloud x86 GPU as backup. Each render also writes an instance-mask pass and a depth pass.

**Ground truth per object:** 3D position, 2D box, visible fraction (visible mask pixels divided by the object's full silhouette), depth, distance to the gripper, and what it rests on or sits inside.

| Family | Example question | Skill tested | Answer type |
| --- | --- | --- | --- |
| Count under clutter | How many mugs are on the table? | Counting | Integer |
| Count by attribute | How many red objects are inside the tray? | Counting, attributes | Integer |
| Nearest to gripper | Which object is closest to the gripper? | Metric depth | Object |
| Distance with scale | About how far is the bottle from the bowl, in cm? (printed grid in view) | Metric estimation | Number with tolerance |
| Front-to-back order | Which is closer to the camera, the apple or the box? | Relative depth | Object |
| Relation in a stated frame | From the camera's view, which object is directly left of the mug? | Spatial relation | Object |
| Support | What is the blue box resting on? | Stacking | Object |
| Containment | Which objects are inside the bowl? | Containment | Set |
| Occlusion | Which object is partly hidden by the bottle? | Occlusion | Object |
| Reachability | Which objects lie inside the green reach zone? | Zone membership | Set |
| Free space | Is there room for the mug between the bowl and the box? (grid in view) | Clearance | Yes or no |
| Gripper view | In the gripper camera, which object is at the centre of the image? | Viewpoint | Object |

**Difficulty controls:** clutter (3 to 25 objects), occlusion level, look-alike objects (same colour, different shape), camera height and angle, lighting (dim, harsh, coloured), camera-quality dial, object size.

**Why errors matter:** a wrong "nearest" or "reachable" answer means the robot grasps the wrong item or collides. A miscount breaks picking and inventory. Misreading support means pulling the bottom box out of a stack.

### Physical twins: real photos with exact answers

1. Print a placement mat with a cm grid and corner markers.
2. Arrange real objects exactly as a generated layout says, using common items that match about 15 of our assets.
3. Photograph from marked camera spots with several phones.
4. Answers come from the layout we placed: exact for counts, relations, containment and occlusion; distances within a tolerance.

About 150 photos is enough to measure how much each model's accuracy drops from rendered to real images. After submission, if a college robotics lab lets us, we repeat it from a real robot arm's camera.

## Factory architecture

The world state is the single source of truth. Both the image and the question are derived from it, so the gates can check one against the other without asking any model.

```text
Domain pack (plugin: schema, sampler, renderers, question families, twin rule)
   | seed
World state = scene file (truth; every answer is computed here)
   |-- draws the image --> Renderer (Blender, headless, seeded: image + mask and depth passes)
   |                          --> Camera simulation (lens, noise, blur, CCTV look)
   |-- asks the question --> Question compiler (typed program on the scene file gives the answer)
Both --> Validation gates G1-G8 (model-free; failures go to the rejected log)
   | pass
Task package (image, question, answer, evidence, gate report, seed)
   --> Evaluation harness (frontier and open models, cached, typed scoring)
   --> Report and risk cards (skill x difficulty, error attribution, intervals)
```

A pack's sampler turns a seed into a world state. The renderer draws it and writes mask and depth passes, while the compiler runs a program on the same state to produce the question and answer. Gates check the image against the state, and only passing tasks are packaged and evaluated.

Rules that hold across the codebase:

- Engine code never contains domain words; packs never contain pipeline logic.
- Everything is a pure function of pack version, seed and parameters, so a task ID is a content hash.
- Twins reuse the same path: perturb the world state, re-render, re-run the gates.
- Formats are versioned, and an exporter maps our task.json to whatever template the organizers publish.

## Validation stack

Every task passes eight gates before it ships, and none of them asks an AI model for the answer. Each gate writes its evidence into the task package. Failed tasks go to a rejected log with the reason.

| Gate | What it proves | How | Evidence written |
| --- | --- | --- | --- |
| G1 Truth by execution | The answer is correct | A typed program runs on the settled scene file; every op has property-based tests (Hypothesis) | Program, trace, answer |
| G2 Second computation | The answer survives an independent route | Recompute it from the rendered mask and depth passes, using pixels rather than scene coordinates; both answers must agree | Both values |
| G3 Evidence visible | Everything the question needs is in the image | Referenced objects are above a visible-fraction threshold and a minimum pixel size; nothing counted is fully hidden; a scale reference is in frame for cm questions | Visible fractions, pixel sizes |
| G4 No near-ties | Exactly one right answer | Compared distances, depths and positions differ by more than both a metric margin and a pixel margin | Margins |
| G5 Vision necessity | The answer can't be guessed without the image | Balanced answer distributions; prior-only and question-only LLM baselines | Blind accuracy per family |
| G6 Counterfactual twin | The answer depends on the scene | Move one object, re-render, re-run: the answer must change and the twin must pass G1–G5 | Twin ID and both answers |
| G7 Determinism | Same seed, same task | Task ID hashes the recipe, versions and seed. Scene files and answers are byte-identical everywhere. Masks and depth must be exactly equal (decoded pixels) on every re-render with the pinned Blender version; they carry all the truth, and G2 recomputes answers from them. Images must match at SSIM 0.999 or above on the default GPU device, and are byte-identical when rendered with the CPU device option | Hashes, SSIM scores |
| G8 Physical twin | A real photo still shows the evidence | Mat corner markers (OpenCV ArUco) map the layout onto the photo, then a human legibility check | Photo-to-layout transform, checker |

**Three design rules behind the gates.**

- **A. Answerable from what's visible.** Ask for centimetres only when the printed grid or a known-size object is in frame; otherwise ask comparisons. Never count, or ask about, objects that are fully hidden.
- **B. No near-ties.** Enforced by G4.
- **C. Honest repeatability.** Enforced by G7, and stated plainly in the README. Exact: scene files and answers (byte-identical everywhere), masks and depth (equal on every re-render). Near-exact: images pass at SSIM 0.999 or above, because GPU path tracing can change a few pixels by one colour level between runs. GPU is the default for speed; the CPU device option gives byte-identical images when they are wanted, for example `vtf verify` on stage.

**Founder audit.** The founder answers a stratified sample of about 150 tasks blind, through a small labelling page; a friend as a second annotator is optional. Target: at least 98% accuracy. Every miss is traced to a generator bug, fixed and logged.

**Dataset-level report.** Gate pass rates, a histogram of rejection reasons, a coverage matrix (skill by camera by difficulty) and answer distributions per family. Showing what the factory throws away is strong evidence of rigour.

Models appear in G5 only as filters, never as the source of an answer. That meets the brief's "independent of the model being evaluated" rule.

For the live demo, run `vtf verify` on stage: rebuild 20 random tasks from their seeds, show matching hashes, then open one rejected task and its reason.

## Evaluation harness

We run three closed frontier models and two open models on the same frozen task set, and report where each one breaks, with confidence intervals.

**Models.** Pick the current flagship vision models from Anthropic, Google and OpenAI, plus two strong open models (for example a Qwen VL model). Pin the exact model IDs on the day you run. The [Vision Arena leaderboard](https://arena.ai/leaderboard/vision) is a quick reference for what's current.

**Protocol.**

- Zero-shot, one fixed system prompt per answer type, final answer returned as JSON.
- Temperature 0 where the API allows; record any reasoning settings.
- Images sent at native resolution; tokens, cost and latency logged per call.
- Two equivalent phrasings of each question on a subset, to measure prompt sensitivity. BlindTest used the same control.

**Scoring.** Typed checkers: exact match after normalising, set match, true/false, and numeric with a tolerance. The tolerance comes from what the image can resolve: object, set and count answers must match exactly; distance answers get a tolerance set by the visible grid spacing. This is stricter and easier to defend than [ChartQA's](https://arxiv.org/abs/2203.10244) flat relaxed accuracy. Unparseable answers count as wrong and are tracked separately.

| Analysis | Question it answers |
| --- | --- |
| Skill-by-model accuracy, 95% bootstrap intervals | What is each model good and bad at? |
| Breakdown by camera and scene condition | Overhead vs gripper camera; clean vs CCTV-quality images |
| Breaking-point curves per difficulty control | At what clutter, occlusion or camera quality does each model fall apart? |
| Rendered-to-real gap | How much does accuracy drop on physical-twin photos of the same layouts? |
| Multi-view consistency | Same scene from three cameras: does the model give consistent answers? |
| Action-risk weighted error | Errors weighted by what they would cost a robot; wrong "nearest" or "reachable" answers weigh most |
| Twin consistency | Does the model get both twins right, or does it miss the change? |
| Vision gain (with image minus blind) | How much does the image actually help each model? |
| Error attribution: wrong depth, wrong object, miscount, invented object, format | Why did it fail? Automatic, because the scene file knows every object |
| Paired comparisons (McNemar test) | Is "A beats B" statistically real? |
| Cost and latency per correct answer | Which model is worth putting on a robot for this job? |

**Engineering.** Async runner with per-provider rate limits and retries. A SQLite cache keyed by task hash, model and prompt version makes reruns free and reproducible. Store raw responses. Use thin SDK adapters, or one gateway (LiteLLM or OpenRouter) to cover many models with one interface.

**Output.** A model risk card per model, styled after Innodata's T&E dashboard: our capability families serve as risk categories, and the difficulty curves play the role of trend lines.

**Budget.** Run a 50-task pilot on every model first to measure real cost per task, then size the full run. Don't guess cost before the pilot.

## Risks and decisions

Keep it a prototype: build directly, fix what breaks, and spend effort only where the judges score or the demo shows.

| Risk | Fallback |
| --- | --- |
| The 3D pipeline blocks us | The same engine switches to financial price charts |
| Rendering too slow on the Mac | Fewer samples plus denoising; overnight renders; DGX Spark or a cloud GPU for volume |
| Images look game-like | Scanned Poly Haven assets, HDRI lighting and path tracing; physical twins prove realism |
| Frontier models ace basic spatial questions | Target exact low-level quantities and clutter; breaking-point curves are findings either way |
| Ambiguous questions (reference frames, hidden objects, near-ties) | Rules A–C, enforced by G3 and G4; every relation names its frame |
| Scope creep (warehouse, CCTV, humanoids) | One scene family until submission; the others become recipes later |
| API cost or rate limits | Small pilot; cache everything; costliest model on a subset |
| Official task format announced late | A converter maps our spec to theirs |

**Decided.**

| Decision | Choice |
| --- | --- |
| Image family | Robot workcell: a tabletop seen through robot cameras, rendered in 3D |
| Image source | Blender only; no AI image generators anywhere in the image path |
| Rendering | Mac first; DGX Spark or a cloud GPU when volume needs it |
| Model access | Own API keys |
| Working style | Prototype and flexible: no licence, compliance or production work; no test gates beyond the checks the judges score |
| Organizer contact | None for now; questions later through their channels |
| Repo | hrishikesh-visual-task-factory, public from day one |
| Team | Founder plus Claude Code; no other humans |
| Task Explorer | Built and hosted on Vercel |
| Pitch | Technical and explicit: beyond 2D, exact 3D truth, robot perception for physical AI |
| Fallback | Financial price charts, only if 3D blocks us |
